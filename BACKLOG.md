# Беклог

Ідеї поза поточним етапом. Не план — черга кандидатів.

## Обкладинки плейлістів

Міняти й генерувати обкладинки. Два різні завдання:

- **Поставити свою картинку** — завантажити готовий файл як обкладинку плейліста.
  **Перевірено 2026-08-02, програмно недоступно:**
  - Веб-API: ендпоінта для артворку бібліотечного плейліста не існує.
  - AppleScript: словник Music.app декларує `artwork` як елемент класу
    `playlist` із записуваним `data`, але реалізації немає. `make new artwork`
    повертає `-10014`, `set data of artwork 1` падає, бо об'єкта немає, і **всі
    плейлісти звітують `artworks=0`** — навіть ті, що показують обкладинку в
    інтерфейсі. Задекларовано, але не працює.

  - Автоматизація інтерфейсу Music.app: **теж недоступна** — Music заблокований
    політикою computer-use, запит на доступ відхиляється автоматично, обходу
    немає.
  - Cider (зрілий відкритий клієнт із повним доступом до веб-шини): мейнтейнер
    у discussions/624 — «Description support is planned, but artwork is not
    currently possible». Найвагоміший доказ, що ендпоінта на цій шині немає.
  - Веб-плеєр: **перевірено емпірично у справжньому залогіненому Chrome.**
    Сторінка плейліста → меню «...» → Edit → діалог «Edit Playlist» містить
    рівно три контроли: назва, опис, галочка «Show on My Profile and in
    Search». **Контролу обкладинки немає.** Веб-плеєр цього не вміє — питання
    закрите.
    (Спроба через Playwright із підсунутим `media-user-token` як кукі теж
    логіниться, але сторінка плейліста віддає помилку — кукі авторизує API,
    веб-плеєру потрібна ще й власна сесія. Для розвідки UI годиться справжній
    браузер.)

  **Непройдений шлях:** перехопити HTTPS нативного Music.app через mitmproxy у
  момент ручної зміни обкладинки й побачити реальний ендпоінт. Ціна — кореневий
  сертифікат у системі (рішення про безпеку, приймає тільки Andrii) і ризик, що
  Apple робить certificate pinning і перехоплення не спрацює.

  Поточний висновок: **публічного програмного шляху не знайдено**. Постановка
  обкладинки лишається ручною: Music.app → правий клік на плейлісті →
  Edit Playlist → перетягнути файл на квадрат → Done.

  **Генерація при цьому автоматизується повністю:** SVG-шаблон → PNG 3000×3000
  через headless Chrome однією командою, див. `covers/`. Тобто в інструменті
  має бути `aimc cover <плейліст>`, що генерує файл і відкриває теку, а останній
  клік робить людина. Перевірити колись, чи веб-плеєр music.apple.com дозволяє
  міняти артворк — не тестувалось.
- **Згенерувати обкладинку** — по вайбу й вмісту плейліста. Тут природньо
  лягає генерація зображення + автоматична постановка з попереднього пункту.

Залежність: спершу перший пункт, бо без можливості поставити картинку генерація
безсенсова.

## Керування не тільки плейлістами

Розширити зону дії з плейлістів на всю бібліотеку:

- **Пісні** — масові операції над бібліотекою, не всередині плейліста: знайти й
  прибрати мертві треки, дублі між альбомами, рейтинги
- **Артисти** — звести одну людину під різними іменами (кейс Yumi Arai /
  Yumi Matsutoya, який ми вже зустріли), подивитись усе одного виконавця
- **Альбоми** — цілі альбоми в бібліотеці, а не окремі треки

## Інші сервіси

Spotify, YouTube Music — через `providers/`. Передумова вже закладена: ISRC як
універсальний ID у спеці плейліста.

## Мобільний доступ — див. Issue #10

Розібрано 2026-08-03: iOS-додаток для вайб-генерації.
Конкуренти (Apple Playlist Playground, PlaylistAI, Playlistable), їхні
дефекти, три варіанти архітектури й що переноситься з цього коду —
все в [Issue #10](https://github.com/avyshnya/ai-music-curator/issues/10).

Коротко: напрямок — вайб-генерація, не гігієна. Телефон не може бути
сервером, тож модель Hevy вимагає власного бекенду. На iOS MusicKit дає
нативно те, що тут добувалося хаками, включно з обкладинкою плейліста.

Нижче — початковий розбір, лишений для історії.

## Мобільний доступ (початковий розбір)

Зараз усе живе на Mac: токен у Keychain, утиліта запускається локально. З
телефону це недосяжно. Чотири шляхи, від дешевого до дорогого:

**1. Claude Code з телефону (claude.ai/code) — не працює.** Сесія виконується в
хмарному контейнері Anthropic, а не на Mac. Токена там немає, Apple Music
недосяжна. Класти туди токен — свідомо винести секрет у чуже середовище.

**2. Тунель до Mac (найдешевше).** Mac лишається виконавцем, телефон лише
командує — наприклад через Tailscale. Умова: Mac увімкнений. Нічого нового
писати майже не треба.

**3. Віддалений MCP-сервер (найчистіше «через Клод»).** Конектори в claude.ai —
це і є віддалені MCP по HTTP. Якщо захостити наш сервер із нормальною
авторизацією й додати як конектор, керування плейлістами працює з телефону,
вебу, звідусіль, будь-яким клієнтом Claude. Ціна: треба хостинг і треба
довірити серверу токен Apple Music.

**4. Нативний iOS-застосунок.** Тут є неочевидний плюс: на iOS MusicKit
працює **краще**, ніж на десктопі — застосунок створює плейлісти за дозволом
користувача, без жодного видобування токенів із браузера. Тобто мобільна
архітектура насправді чистіша. Ціна: Swift, App Store і $99/рік Apple Developer,
щоб застосунок жив на пристрої довше за 7 днів.

Здогад Andrii про поділ «харнес у застосунку, інтелект через API до Claude»
правильний — саме так це і будується. Але це окремий проєкт, не продовження
поточного.

**Рекомендація:** зараз не робити. Якщо телефон знадобиться швидко — варіант 2.
Якщо проєкт доживе до публічного релізу — варіант 3.
